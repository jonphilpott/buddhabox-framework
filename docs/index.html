BuddhaBox

A header-only audio DSP framework for the STM32F401 Black Pill and an I2S DAC: 79 classes, from simple oscillators to Mutable Instruments' resonators, reverbs and drums.

Overview

BuddhaBox began as one generative ambient instrument. This framework separates its reusable parts from that patch and adds ports of the components in Mutable Instruments' firmware (via the Partials library) that fit the Black Pill's 84 MHz Cortex-M4 and 64 KB of RAM.

Design principles

  • Sample by sample. Every module has a process() method that handles exactly one sample. You wire modules together in plain C++, like patching a modular synth.
  • Header-only. Modules live in .h files so the compiler can inline the per-sample code. Only the audio engine has a .cpp.
  • Floats, normalised to ±1. All audio is float from -1.0 to 1.0. Conversion to 16-bit happens once, in your audio callback.
  • No dynamic memory. Buffers are fixed-size arrays, sized by template parameters (Reverb<8192>), so PlatformIO's RAM report tells you the true cost at build time.
  • Tables in flash. Lookup tables (sine, curves, wavefolders) are static const arrays generated ahead of time, so they cost flash (256 KB, mostly free) instead of RAM.
  • 16-bit delay storage. Delay lines store int16_t where the signal allows, halving their RAM.

Quick start

1. Create a project

The quickest start is the project generator. It makes a folder with a platformio.ini linked to this checkout and a src/main.cpp copied from one of the examples:

python3 tools/new_project.py ../my_synth
python3 tools/new_project.py ../bells --example custom_voice
cd ../my_synth && pio run

To add the framework to an existing PlatformIO project instead, point lib_deps at this repository. A symlink:// path uses your local checkout directly, so edits to the framework show up immediately:

[env:myproject]
platform = ststm32@15.4.1
board = blackpill_f401cc
framework = arduino
upload_protocol = dfu
build_unflags = -Os
build_flags =
    -O2
    -D PIO_FRAMEWORK_ARDUINO_ENABLE_CDC
    -D USBCON
lib_deps =
    symlink://../buddhabox-framework

build_unflags = -Os matters: the STM32 core adds -Os (optimise for size) after your build_flags, and GCC obeys the last -O it sees, so without it -O2 is silently ignored and the DSP runs slower.

2. Write a patch

Every program has three parts: DSP objects as globals, an audioCallback() that fills the DAC's buffer, and a setup() that starts the engine. This is examples/minimal/main.cpp:

/**
 * @file main.cpp
 * @brief The smallest complete BuddhaBox program: one sine tone.
 *
 * Every BuddhaBox program has the same three parts:
 * 1. DSP objects as globals (allocated at compile time, never with new).
 * 2. audioCallback(): called by the DMA interrupt whenever the DAC needs
 *    another block of samples. Fill the buffer one stereo frame at a time.
 * 3. setup(): configure the objects, then start the audio engine.
 *
 * Wiring: PB12 -> LRCLK/WSEL, PB13 -> BCLK, PB15 -> DIN on the UDA1334A.
 */

#include <Arduino.h>

#include "buddhabox/engine/audio_engine.h"
#include "buddhabox/osc/oscillator.h"

using namespace bb;

// 1. DSP objects.
Oscillator osc;

/**
 * Fill one block of audio. Runs in interrupt context: no Serial, no
 * analogRead(), no allocation.
 *
 * @param buffer  Interleaved stereo int16 samples [L, R, L, R, ...]
 * @param length  Number of int16 values (frames * 2)
 */
void audioCallback(int16_t *buffer, uint16_t length) {
  for (uint16_t i = 0; i < length; i += 2) {
    // DSP works in floats from -1.0 to 1.0; convert to 16-bit only here,
    // with a little headroom (32000 rather than 32767).
    float sample = osc.process();
    int16_t s = (int16_t)(clampf(sample, -1.0f, 1.0f) * 32000.0f);
    buffer[i] = s;     // left
    buffer[i + 1] = s; // right
  }
}

void setup() {
  // 3. Configure, then start the DMA. Audio begins immediately.
  osc.setWaveform(Waveform::SINE);
  osc.setFrequency(220.0f);
  osc.setAmplitude(0.5f);
  AudioEngine::begin();
}

void loop() {
  // Nothing to do: the interrupt keeps the audio flowing. Read pots or
  // buttons here and pass the values to the DSP objects.
}

3. Build and upload

  1. pio run to build (it must compile cleanly before you flash).
  2. Put the Black Pill in DFU mode: hold BOOT0, press and release NRST, release BOOT0.
  3. pio run -t upload.
  4. Optional: pio device monitor to read Serial output, such as the CPU meter.
Is my patch too heavy? Call AudioEngine::cpuLoad() from loop() and print it. It reports the fraction of each audio block the callback used, measured with the Cortex-M4's cycle counter. Keep it below about 0.8. AudioEngine::cpuPeak() gives the worst block since its last call, which catches spikes a once-a-second print would miss. Above 1.0 the audio clicks, and loop() stops running altogether, so nothing gets printed. So the engine lights the Black Pill's blue LED (PC13) the first time a block runs late, and leaves it on until reset; run the profile example to see where the cycles go. To turn the LED off, for example to use PC13 yourself or with UserLED, which drives the same pin, add -D BB_OVERRUN_LED=0 to build_flags.

Conventions

Every module works out of the box

Constructors set sensible defaults, so a global Svf filter; is ready to use. The modules ported from Mutable Instruments also have init(float sampleRate = SAMPLE_RATE), which resets them to silence; you only need to call it to restart a voice.

process() comes in a few shapes

Control rate versus audio rate

Setters that call expf(), powf() or tanf() say so in their docstring. Call those from setup, from loop(), or every 16–64 samples inside the callback, rather than every sample. Per-sample paths use table lookups and the fast fastExp2()/fastLog2() in core/dsp_common.h.

Treat these as a rough guide. Each figure is one module timed on its own. In a full patch, modules share the flash cache, the compiler lays code out differently and interrupts arrive, so the same module can cost more. Adding up the table can badly underestimate a patch: patch_demo adds up to 75% but measures 98%. Use the table to compare modules and spot the expensive ones, then check the real patch with AudioEngine::cpuLoad().

The resonator dominates. It costs about 115 cycles plus 49 per mode, so 24 modes alone use two-thirds of the CPU. 12–16 modes is plenty for bells and bowls.

Some modules cost more when they work harder. The limiter costs about 40 cycles when the signal is below its threshold and about 100 while it is limiting. Reverb costs about 5% more with loud input than quiet. Budget for the busy figure.

Modulating a parameter costs its setter, every time. Most setters that change a filter's cutoff use tanf() or similar maths, and cost several times the filter itself: Svf::process() is 18 cycles, Svf::setFrequency() 170. Update such parameters at control rate, for example once every 32 samples, which brings a 170-cycle setter down to about 5 cycles per sample. Where a fast form exists, use it: setCoefficients(..., TanApprox::Fast) is 56 cycles.

Large patches can stop the compiler inlining. GCC stops inlining into a function once it passes a size limit. A very large audioCallback() could then call big modules instead of inlining them, which made some modules up to 2.5× slower in testing. If cpuLoad() is well above the sum of these figures, move groups of modules into voice classes (see below), which keeps each function small.

Composing new modules

You extend the framework by writing classes in your own project, not by editing it. There are two patterns.

Pattern 1: a voice class that owns modules

Wrap a few modules in a class with a small, musical interface. The class owns its parts as members (so their memory is fixed at compile time), configures them in its constructor, and wires them in its own process().

strike()one-sample impulse → ModalResonator8 modes, bell-like → VactrolLpgdarkens as it decays → process()

BellVoice: the class below hides two modules behind setPitch(), strike() and process().

Pattern 2: an effect built on FxEngine

FxEngine<SIZE> is the toolkit Reverb, Chorus, Ensemble, Diffuser and PitchShifter are written with. You declare delay lines in one shared buffer, then each sample run a tiny "program" on an accumulator: read() values in, write() them to lines, lp()/hp() to filter.

left in→ left line→ right out ↔ left out← right line← right in

PingPongEcho: each line feeds the other, so every repeat bounces to the opposite side.

The complete example

Both classes, and a patch that plays two bells through the echo (examples/custom_voice/main.cpp, built by pio run -e custom_voice):

/**
 * @file main.cpp
 * @brief Composition example: build your own voice and your own effect.
 *
 * Two patterns for extending the framework without touching it:
 *
 * 1. A voice class (BellVoice) that owns existing modules and exposes a
 *    small, musical interface: setPitch(), strike(), process().
 * 2. An effect class (PingPongEcho) written on FxEngine, the same toolkit
 *    the Reverb and Chorus are built with.
 *
 * The patch: two bells play notes chosen by a RandomSequence and snapped
 * to a pentatonic scale by a Quantizer, into a ping-pong echo, then a
 * limiter.
 */

#include <Arduino.h>

#include "buddhabox/core/dsp_common.h"
#include "buddhabox/dynamics/vactrol_lpg.h"
#include "buddhabox/engine/audio_engine.h"
#include "buddhabox/fx/fx_engine.h"
#include "buddhabox/fx/limiter.h"
#include "buddhabox/mod/clock.h"
#include "buddhabox/mod/quantizer.h"
#include "buddhabox/mod/random_sequence.h"
#include "buddhabox/physical/modal_resonator.h"

using namespace bb;

/**
 * A struck bell: a modal resonator through a vactrol low-pass gate.
 *
 * The resonator rings; the gate adds the natural "darkening" of a real
 * decay (quieter and duller together). Each strike is a one-sample
 * impulse into the resonator plus a ping of the gate.
 *
 * Example:
 *   BellVoice bell;
 *   bell.setPitch(440.0f);
 *   bell.strike(0.8f);
 *   float s = bell.process();
 */
class BellVoice {
public:
  BellVoice() {
    // 8 modes: about 510 cycles per bell, measured (12 would be 700).
    resonator_.setModes(8);
    resonator_.setStructure(0.2f); // bell-like, slightly inharmonic
    resonator_.setDamping(0.75f);
    resonator_.setPosition(0.3f);
    lpg_.setDecay(0.8f);
    lpg_.setColour(0.6f);
  }

  /**
   * Tune the bell.
   * @param hz  Fundamental in Hz
   */
  void setPitch(float hz) {
    resonator_.setFrequency(hz);
    lpg_.setAttackPitch(hz); // higher bells open faster, as in Plaits
  }

  /**
   * Strike the bell.
   * @param velocity  0.0 to 1.0
   */
  void strike(float velocity) {
    impulse_ = velocity;
    lpg_.trigger();
  }

  /**
   * Generate the next sample.
   * @return  The bell, about ±1
   */
  float process() {
    float excitation = impulse_;
    impulse_ = 0.0f; // the strike lasts exactly one sample
    return lpg_.process(resonator_.process(excitation));
  }

private:
  ModalResonator<> resonator_;
  VactrolLpg lpg_;
  float impulse_ = 0.0f;
};

/**
 * Stereo ping-pong echo written on FxEngine.
 *
 * Two delay lines cross-feed: the left echo feeds the right line and
 * vice versa, so each repeat bounces to the other side.
 *
 * @tparam SIZE  FxEngine buffer (power of two); RAM = SIZE * 2 bytes
 *
 * Example:
 *   PingPongEcho<8192> echo;
 *   float l = in, r = in;
 *   echo.process(l, r);
 */
template <uint32_t SIZE = 8192> class PingPongEcho {
public:
  PingPongEcho() {
    // Declare the lines once, then allocate: each line is just a region
    // of the shared buffer. Half the buffer each, minus the gap samples.
    left_ = engine_.addDelay(SIZE / 2 - 2);
    right_ = engine_.addDelay(SIZE / 2 - 2);
    engine_.allocate();
  }

  /** @param x  Feedback per bounce, 0.0 to 0.9 */
  void setFeedback(float x) { feedback_ = clampf(x, 0.0f, 0.9f); }

  /** @param x  Wet amount, 0.0 to 1.0 */
  void setAmount(float x) { amount_ = x; }

  /**
   * Process one stereo sample in place.
   * @param left   Left in/out
   * @param right  Right in/out
   */
  void process(float &left, float &right) {
    FxEngine<SIZE> &c = engine_;
    float echoL, echoR;
    c.start(); // advance every line by one sample
    // Left line: the dry left plus feedback from the right line's tail.
    c.read(left, 0.5f);
    c.readTail(right_, feedback_);
    c.write(left_, 0.0f);
    // Right line: the dry right plus feedback from the left line's tail.
    c.read(right, 0.5f);
    c.readTail(left_, feedback_);
    c.write(right_, 0.0f);
    // Outputs: each side hears the *other* line's tail.
    c.readTail(right_, 1.0f);
    c.write(echoL, 0.0f);
    c.readTail(left_, 1.0f);
    c.write(echoR, 0.0f);
    left += amount_ * echoL;
    right += amount_ * echoR;
  }

private:
  FxEngine<SIZE> engine_;
  typename FxEngine<SIZE>::Delay left_, right_;
  float feedback_ = 0.5f, amount_ = 0.4f;
};

// ── The patch ───────────────────────────────────────────────────────────
const int kNumBells = 2; // about 54% of the CPU for both
BellVoice bells[kNumBells];
PingPongEcho<8192> echo; // 16 KB: about 93 ms per side
Limiter limiter;
TempoClock clock8(84.0f, 2); // eighth notes at 84 BPM
RandomSequence melody;
Quantizer scale;
Random rng;
int nextBell = 0;

/**
 * On each eighth note, maybe strike the next bell at a new pitch.
 */
void onTick() {
  if (rng.uniform() > 0.6f)
    return;                                       // leave space
  float pitch = 1.5f * melody.next();             // 0 to 1.5 octaves
  float q = scale.process(pitch, 0.7f);           // snap to the scale
  bells[nextBell].setPitch(220.0f * fastExp2(q)); // from A3
  bells[nextBell].strike(0.5f + 0.5f * rng.uniform());
  nextBell = (nextBell + 1) % kNumBells; // round-robin voices
}

/**
 * Fill one block of audio.
 * @param buffer  Interleaved stereo int16 samples
 * @param length  Number of int16 values (frames * 2)
 */
void audioCallback(int16_t *buffer, uint16_t length) {
  for (uint16_t i = 0; i < length; i += 2) {
    if (clock8.process())
      onTick();
    float mix = 0.0f;
    // Gain 2.0, set from a host simulation: a one-sample strike puts
    // little energy into a resonator, so the bells peak near 0.42,
    // leaving room for the echo's repeats on top.
    for (int b = 0; b < kNumBells; ++b)
      mix += bells[b].process() * 2.0f;
    float left = mix, right = mix;
    echo.process(left, right);
    limiter.process(left, right);
    buffer[i] = (int16_t)(left * 32000.0f);
    buffer[i + 1] = (int16_t)(right * 32000.0f);
  }
}

void setup() {
  scale.init(Quantizer::preset(Quantizer::PENTATONIC));
  melody.setLength(8);
  melody.setDejaVu(0.3f);
  echo.setFeedback(0.55f);
  Serial.begin(115200);
  AudioEngine::begin();
}

/** Print the measured CPU load once a second (pio device monitor). */
void loop() {
  Serial.print("CPU: ");
  Serial.print(AudioEngine::cpuLoad() * 100.0f, 1);
  Serial.print("%  peak: ");
  Serial.print(AudioEngine::cpuPeak() * 100.0f, 1);
  Serial.println("%");
  delay(1000);
}

Key principles

  • Own, don't allocate. Members and template sizes, never new. Arrays of voices (BellVoice bells[3];) give you polyphony.
  • Exciter into resonator. Most physical sounds are a short burst (Dust, Plucker, an impulse, noise through an envelope) into something that rings (ModalResonator, StringModel, Svf with high Q).
  • Modulate at control rate. Update slow parameters every 16–64 samples with a counter, as examples/singing_bowls does.
  • Finish with a Limiter. Resonators and feedback can exceed ±1; the limiter keeps the 16-bit conversion from clipping.

Random strikes on a bell-like resonator, glassy pings and a filtered string-machine drone. A Lorenz attractor drifts the timbre so the patch never repeats. The composition example above.

compile_all

Not musical: instantiates every class so pio run -e compile_all proves the whole framework builds, and reports the combined RAM and flash.

profile

Measures each module's cost on the board, in cycles per sample and as a share of the 1,905-cycle budget, and prints a table over USB serial every few seconds. It never starts the audio engine. A patch over 100% starves loop(), so its own meter can never print; the profiler reports regardless. The modules are set up as in singing_bowls, and the last row predicts that patch's load. Copy its PROFILE() macro to time your own code.

pio run -e profile -t upload
pio device monitor

profile_all

Measures every audio module, plus the setters a patch calls when it modulates a parameter, and prints CSV for tools such as a patch editor to read. It refines profile in four ways: interrupts are off while timing, each module keeps the fastest of five runs, the cost of the empty loop is subtracted, and each module is timed in its own small function so the compiler inlines it as it would in a real patch. Drums and plucks are re-struck and envelopes re-gated every 2,048 samples, so each module is timed while it sounds.

A wire's target is one of three things:

TargetExampleWhat the generated code does

How a setter cable works

A setter cable moves a value up and down around a centre. The centre is the setter's set value (the "starting value" in the editor); the cable's amount is how far each 1.0 of signal moves it. A filter set to 800 Hz, with an LFO cable of amount 300:

"filt": {"type": "Svf", "set": {"setFrequency": [800, 0.7]}}
["lfo.out", "filt.setFrequency", {"amount": 300}]

// becomes, every control_every samples:
filt.setFrequency(800.0f + 300.0f * lfo_v_, 0.7f);

The LFO swings from −1 to 1, so the cutoff swings from 500 to 1,100 Hz. A knob gives 0 to 1, so the same cable from a knob would turn 800 to 1,100 Hz. With no set value the centre is 0 and the cable alone sets the value. The editor writes this formula on each dashed cable and lists what comes out at −1, 0, ½ and 1.

The steps are even, which suits levels, mixes and times. Pitch and cutoff need a curve: the ear hears 100 to 200 Hz as the same step as 1,000 to 2,000 Hz. For those, put a Range in between:

"cutRange": {"type": "Range",
             "set": {"setOutput": [80, 8000], "setExponential": true}}
["knob.out", "cutRange.in"],
["cutRange.out", "filt.setFrequency"]

Now each sixth or so of the knob's turn is one octave, and halfway is 800 Hz rather than the 4,040 Hz a straight line gives. Range also takes an LFO's −1 to 1 (setInput(-1, 1)) and runs backwards if its ends are swapped. Cables into one input add up; to add signals once and send the sum to several places, use a Mixer (four inputs, levels set by the cable amounts, chained for more). Cables only add, so to let one signal scale another (a knob setting an LFO's depth, an envelope as a VCA) use Multiply. All three live in util/, with Param (below).

Modulating at control rate is what makes it affordable: a filter's setFrequency() costs 170 cycles, or about 5 per sample when called every 32 samples. Wires may not form a loop.

The tool prints a rough estimate of the patch's CPU and RAM and warns above 80% of the CPU or over 64 KB of RAM. CPU comes from the measured costs above (the resonator's from its setModes value, about 115 + 49 per mode), plus each modulated setter's cost divided by control_every. RAM includes the framework's own 6 KB and scales each buffer to its template size. The RAM estimate is close; the CPU estimate is a rough guide and can be well below the real load. The build reports the real RAM, and the starter main.cpp prints the real CPU.

examples/patch_demo uses all three kinds: a clock triggers a pluck, dust strikes a resonator whose structure a Lorenz attractor modulates, an LFO sweeps a filter on a string drone, and all three share a reverb. The tool estimates 75% of the CPU and 43 KB of RAM; on the board it measures about 98% of the CPU (clean audio, little headroom) and the build reports 42.5 KB.

["clock.out", "pluck.trigger"],
["chaos.out", "bowl.setStructure", {"amount": 0.3}],
["lfo.out", "filt.setFrequency", {"amount": 300}],
["filt.lp", "verb.left", {"amount": 0.3}]

patch_graph.h puts every module in namespace patch, so main.cpp reaches them as patch::osc. The starter main.cpp prints cpuLoad() and cpuPeak() over USB serial once a second, to check the estimate. Names the generator invents end in _ (osc_v_), so module ids may not. The tool writes main.cpp only if it does not exist, so your code there is never overwritten.

Each module's inputs, outputs and setters come from tools/modules.json, which tools/gen_modules.py reads from the headers: process() arguments are inputs; its return value (or each field of a returned struct, or left/right for stereo effects) is an output, as is each float name() const getter; each setX() is a setter. Costs come from tools/costs.csv, the saved output of profile_all. Rerun gen_modules.py after changing a module's API or re-profiling.

patch_param: playing a patch from main.cpp

Every module is a global in namespace patch, so main.cpp can call patch::env.trigger() or patch::osc.setFrequency(220.0f) directly. Two things decide whether that works:

  • Cables win. The generated code rewrites every setter and event a cable drives: setters every control_every samples, events every sample. Call such a setter from main.cpp and the patch overwrites it within a millisecond.
  • Where the code runs. Code in audioCallback(), beside patch::process(), is sample-accurate and cannot be interrupted, but must be quick: no Serial, no analogRead(). Code in loop() can be slow, but the audio interrupt can cut in halfway through a call that changes several fields of a module.

Param solves both. It is a value with an out jack: place it in the patch, cable it wherever the value should go, and set it from main.cpp. Because it goes through cables, it can pass through a Range or be mixed with an LFO like any other signal. It is safe to set from loop(): it stores one float and one flag, and the processor writes each in a single instruction.

CallWhat the patch sees
patch::note.setValue(330.0f)330 from the next sample on
patch::strike.pulse()1.0 for exactly one sample, then the value again: fires anything cabled to a trigger

Use pulse() for triggers rather than setValue(1) then setValue(0): from loop(), both writes can fall between two samples, and the patch never sees the 1. examples/patch_param runs a four-note sequencer in loop(). Its note Param sets the pitch, an LFO adds ±3 Hz of vibrato on the same cable target, and its strike Param triggers an envelope into a Multiply used as a VCA:

// patch.json
"note":   {"type": "Param", "set": {"setValue": 220}},
"strike": {"type": "Param"},
["note.out", "osc.setFrequency"],
["vibrato.out", "osc.setFrequency", {"amount": 3}],
["strike.out", "env.trigger"],

// main.cpp, in loop()
if (millis() - lastStep >= 300) {
  lastStep = millis();
  patch::note.setValue(notes[step++ & 3]);
  patch::strike.pulse();
}

Porting notes: Partials to BuddhaBox

The Mutable Instruments modules come from the Partials library, which targets desktop VCV Rack plugins. Running them on the Black Pill needed these changes:

  • Heap to fixed arrays. std::vector buffers became template-sized arrays (Reverb<SIZE>, StringModel<MAX_DELAY>, Tube<SIZE>, ModalResonator<BOW_DELAY>).
  • RAM tables to flash. Tables Partials computed at start-up are generated by tools/gen_tables.cpp as static const arrays. Tides' 57 KB of Slope tables alone would not have fitted in RAM.
  • 16-bit effect buffers. FxEngine stores int16_t scaled to ±4 (reverb internals reach about ±2.3), giving a noise floor near -89 dBFS. The bowed-mode delays stay float: their signal is tiny and the loop resonant, so 16 bits audibly changed the tone.
  • Buffers that fit. When a template size is smaller than an effect's original delays, every delay shrinks in proportion (fitScale()), giving a smaller room rather than a crash.
  • No per-sample transcendentals. exp(), pow(), log10(), sin() and tanh() in per-sample code became table reads, fastExp2()/fastLog2() or rational approximations. Double-precision maths (software-emulated on the M4) was removed from everything except one-off filter design in Hilbert::init().
  • One namespace. Everything is in bb. Clashing names were renamed: Partials' Envelope is SegmentEnvelope, LowPassGate is VactrolLpg, Wavefolder is TableWavefolder, and String is StringModel (Arduino already has a String).
  • Speed-ups. After measuring on the board, Hilbert runs its two chains interleaved (bit-identical, 34% faster), ModalResonator runs its modes in pairs, and Svf shares its products (20% faster together). Build with build_unflags = -Os: the STM32 core's -Os otherwise overrides -O2.
  • A bug fixed. Partials' Particle dropped Plaits' 1 / density impulse gain, so sparse particles were almost silent (below 0.00003 at 1 Hz). It is fixed in both libraries, and Partials has a test for it.
  • Defaults. Every class constructs itself at SAMPLE_RATE (44.1 kHz); ModalResonator defaults to 24 modes instead of 64.
  • Not ported. Vocoder (160 filters, far too heavy), OnsetDetector (needs an audio input), WAV and sample buffers (no file system, no spare RAM), and Wavetable (heap-based; easy to add as a flash table when needed).
